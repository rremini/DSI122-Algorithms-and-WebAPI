## นิยามแบบ Recursive Definition ของ Factorial
Factorial function  เป็นตัวอย่างคลาสสิกของ **recursive definition** (นิยามเวียนเกิด — การนิยามสิ่งหนึ่งโดยอ้างอิงถึงตัวมันเอง) ซึ่งประกอบด้วย 2 ส่วนเสมอ:

- **Base case / Anchor** (กรณีฐาน — จุดที่การเวียนเกิดหยุดโดยไม่เรียกตัวเองอีก): `0! = 1`
- **Inductive step** (ขั้นตอนอุปนัย — กฎที่สร้างค่าใหม่จากค่าที่เล็กกว่า): `n! = n × (n-1)!` เมื่อ n > 0

เขียนเป็นโค้ด Java ได้ว่า:
```java
long factorial(long n) {
    if (n == 0)
        return 1;
    else 
        return n * factorial(n-1);
}
```
เวลาคำนวณ `3!` จะเกิดการ "คลี่" (unwind) ของสมการดังนี้:
```
3! = 3 × 2!
   = 3 × (2 × 1!)
   = 3 × (2 × (1 × 0!))
   = 3 × (2 × (1 × 1))
   = 6
```
สังเกตว่าค่าจะยังคำนวณไม่เสร็จจนกว่าจะไปถึง base case (0! = 1) ก่อน แล้วค่อยทบกลับ (return) ย้อนขึ้นมาคูณกันทีละชั้น

### ความสัมพันธ์กับ Call Stack
ทุกครั้งที่ method เรียกตัวเอง ระบบจะสร้าง **Activation Record** (หรือ **Stack Frame** — พื้นที่ความจำที่เก็บข้อมูลของการเรียก method หนึ่งครั้ง) ขึ้นมาบน **Call Stack** (สแตกที่เก็บลำดับการเรียก method) ซึ่งแต่ละ Activation Record จะเก็บ:
- ค่า parameter ที่ส่งเข้ามา (เช่น ค่า n)
- Local variable (ตัวแปรภายใน method)
- **Return address** (ตำแหน่งที่ต้องกลับไปทำงานต่อหลังจบ method นี้)
- **Dynamic link** (ตัวชี้กลับไปยัง Activation Record ของผู้เรียก)
- ค่า return value

เมื่อเรียก `factorial(3)` จะเกิดขั้นตอนดังนี้:
**Push** — สแตกจะถูก Push เพิ่ม frame ใหม่ทุกครั้งที่เรียกซ้ำ โดยแต่ละ frame ยังไม่รู้ค่า return เพราะรอ call ถัดไปให้เสร็จก่อน:
```
factorial(3)  n=3, ผลลัพธ์ = ?
  factorial(2)  n=2, ผลลัพธ์ = ?
    factorial(1)  n=1, ผลลัพธ์ = ?
      factorial(0)  n=0, ผลลัพธ์ = 1  ← ถึง base case
```

**Pop** — เมื่อถึง base case แล้ว แต่ละ frame จะคำนวณเสร็จแล้ว "ถูกดึงออก" (pop) จากสแตก พร้อมส่งค่ากลับไปให้ frame ที่เรียกมัน

```
factorial(0) return 1        → กลับไปที่ factorial(1)
factorial(1) return 1×1 = 1  → กลับไปที่ factorial(2)
factorial(2) return 2×1 = 2  → กลับไปที่ factorial(3)
factorial(3) return 3×2 = 6  → จบ
```

นี่คือเหตุผลที่ Call Stack สำคัญมากในการเข้าใจ recursion: มันแสดงให้เห็นว่าเหตุใด recursion ถึงใช้หน่วยความจำมากกว่าการวนลูปแบบ iterative (แต่ละ call ยังค้างอยู่ในสแตกจนกว่าจะ return) และหากเวียนเกิดลึกเกินไปโดยไม่มี base case ก็จะเกิด **Stack Overflow** (สแตกล้น เพราะ push ไปเรื่อยๆ ไม่มีการ pop)

## Tracing Recursion — หลักการและเหตุผลที่ต้องเรียนรู้
**Tracing recursion** (การไล่ดูลำดับการทำงานของ recursion) จำเป็นเพราะ recursive function มักมี **execution order** (ลำดับการทำงาน) ที่ไม่ตรงไปตรงมาเหมือนโค้ดแบบ sequential — โค้ดบรรทัดเดียวกันอาจถูกเรียกหลายรอบในบริบทที่ต่างกัน การ trace ช่วยให้:
1. คาดเดา output ได้ถูกต้องก่อนรันจริง
2. debug ได้ง่ายขึ้นเมื่อผลลัพธ์ผิดพลาด
3. เข้าใจว่า call ไหนเกิดก่อน-หลัง และค่าตัวแปรในแต่ละ call ต่างกันอย่างไร (เพราะแต่ละ call มี Activation Record แยกกัน)
จากเอกสาร ใช้ฟังก์ชันตัวอย่างนี้:
java

```java
void f(int n) {
    if (n > 0) {
        f(n-1);
        System.out.print(n + " ");
        f(n-1);
    }
}
```

ฟังก์ชันนี้เรียกตัวเอง **2 ครั้ง** ต่อ 1 call (ไม่ใช่แค่ครั้งเดียวแบบ factorial) ทำให้การไล่ตามด้วยตาเปล่ายากขึ้นมาก — นี่คือเหตุผลที่ต้องมีเทคนิคช่วย trace

---

### วิธีที่ 1: Tracing ด้วย Indentation (การเยื้องบรรทัด)
หลักการ: ทุกครั้งที่เข้าไปใน call ที่ลึกขึ้น ให้เยื้อง (indent) บรรทัดเพิ่มขึ้นหนึ่งระดับ เพื่อแสดง "ความลึก" ของการเรียกและลำดับเวลาที่แต่ละคำสั่งทำงานจริง
ตัวอย่าง `f(2)`:
```
f(2)
  f(1)
    f(0)
    1
    f(0)
  2
  f(1)
    f(0)
    1
    f(0)
output: 1 2 1
```

วิธีนี้ดีตรงที่มัน **ตรงกับลำดับเวลาจริง** (chronological order) ของการทำงาน — อ่านจากบนลงล่างแล้วเห็น output ตามลำดับที่ print จริง จึงเหมาะกับการเข้าใจ "อะไรเกิดก่อนเกิดหลัง" คล้ายการไล่ดู log การทำงาน

### วิธีที่ 2: Tracing ด้วย Tree of Calls (ต้นไม้ของการเรียก)
หลักการ: วาดเป็นแผนภาพต้นไม้ (tree diagram) โดยแต่ละ node คือหนึ่ง call แล้วแตกกิ่ง (branch) ออกไปตาม call ย่อยที่มันเรียก

ตัวอย่าง `f(2)` ในรูปแบบ tree:

```
              f(2)
           /    |    \
       f(1)     2     f(1)
      /  |  \       /  |  \
   f(0)  1  f(0)  f(0)  1  f(0)
```

วิธีนี้ดีตรงที่ทำให้ **เห็นภาพรวมโครงสร้าง** (structure) ของการเรียกทั้งหมดในครั้งเดียว เหมาะกับการวิเคราะห์ เช่น นับจำนวน call ทั้งหมด หรือดูว่ามี call ที่ซ้ำซ้อน (redundant calls) กี่ครั้ง — ซึ่งนำไปสู่แนวคิดเรื่อง **Excessive Recursion** (การเวียนเกิดที่มากเกินจำเป็น) ที่พูดถึงต่อไป

**เปรียบเทียบสองวิธี:**

||Indentation|Tree of Calls|
|---|---|---|
|จุดเด่น|เห็นลำดับเวลา/output ตามจริง|เห็นโครงสร้างและปริมาณ call โดยรวม|
|เหมาะกับ|debug ตามลำดับการรัน|วิเคราะห์ประสิทธิภาพ/ความซับซ้อน|

## ตัวอย่างในโลกจริง: Fibonacci และปัญหา Excessive Recursion

```java
int Fib(int n) {
    if (n < 2) return n;
    else return Fib(n-2) + Fib(n-1);
}
```

เอกสารแสดง **tree of calls** ของ `Fib(6)` ให้เห็นว่า `Fib(2)` ถูกเรียกซ้ำหลายครั้งโดยไม่จำเป็น (F(3), F(2) วนซ้ำในหลายกิ่ง) นี่คือตัวอย่างจริงที่การ trace ด้วย tree ช่วยให้ "มองเห็น" ปัญหาด้วยตา — จากตาราง Figure 5-9 ใน slide: `Fib(30)` ใช้ recursive call ถึง **2,692,537 ครั้ง** เทียบกับวิธี iterative ที่ใช้เพียง **87 assignment** เท่านั้น

นี่คือเหตุผลเชิงปฏิบัติที่ต้องเรียน tracing recursion — ไม่ใช่แค่เพื่อความเข้าใจทางทฤษฎี แต่เพื่อ**ตรวจจับปัญหาประสิทธิภาพ**ก่อนที่โค้ดจะถูกนำไปใช้จริงและทำงานช้าเกินไป
